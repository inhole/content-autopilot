# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Content Autopilot is a personal internal tool, not a SaaS. It collects AI and developer news from RSS, has an LLM pick topics and write Korean Threads posts, sends each draft to a Telegram bot for approval, and publishes approved posts at fixed time slots. The Threads pipeline covers **Threads only**. A second pipeline handles **trial campaigns (체험단)** from two sources: **Kakao gift trials (카카오톡 선물하기 체험단)**, read from the public list on gift.kakao.com, and **Musinsa preuser trials (무신사 프리유저 체험단)**, read from the public list API of musinsa.com/preuser (no login). It ranks them, sends photo cards to Telegram, and tracks apply / result / review deadlines and the review draft. The owner applies and writes the review by hand (Kakao: mobile app, Musinsa: PC) and records each step with a Telegram button; the code never applies or posts anything yet. Neither pipeline **uses n8n**: all scheduling and retries live in this codebase on pg-boss, in one cloud worker. (Applying to Musinsa needs the owner's login; a later phase may drive that through the Aside browser on the owner's PC.) The campaign plan and its status are in `docs/plans/campaign-autopilot.md`; remaining work and next plans (reviving expired drafts, the React dashboard, Shorts/Reels) are in `docs/plans/roadmap.md`.

Human-facing docs (Korean) live in `docs/`: `setup.md` (external services and tokens), `architecture.md`, `operations.md` (CLI, troubleshooting, deployment), `decisions.md` (why Threads-only and no n8n, plus the roadmap), `dashboard.md` (web dashboard and its Telegram-code login), `aside.md` (Aside Browser scripts) and `conventions.md`. Update them when behavior they describe changes.

**Commit messages must follow `docs/conventions.md`:** `<type>: <Korean summary>`, e.g. `feat: Telegram 검수 메시지에 수정 답장 기능 추가`. The type is one of feat, fix, docs, refactor, test, chore or perf, and an optional body explains why. A commit-msg hook (`.githooks/commit-msg` → `scripts/commit-msg.mjs`, enabled by `npm install` via `prepare`) rejects non-conforming messages. Fix the message instead of bypassing the hook with `--no-verify`. Code, comments and logs stay in English; prompts, Telegram text and `docs/` are in Korean.

A script's leading `//` comment is its description and `// args: a, b?` declares its args (undeclared or missing required ones are rejected); the body runs as an async function with `args` in scope (`wrapScript` in `src/aside/client.ts`). Config is loaded from `.env` (see `.env.example`) and validated in `src/config.ts`. An empty `KEY=` line counts as unset.

## Architecture

The pipeline is a chain of pg-boss queues, all defined in `src/jobs.ts`:

```
daily-pipeline (cron) → collect → rank (expire stale, score, flag duplicates) → enqueue generate for every SHORTLISTED topic without a post
generate-v2 {topicId, regenerate?, feedback?} (policy singleton per topic) → posts row PENDING_REVIEW → enqueue review
review {postId}           → Telegram message with approve / regen / reject buttons
  approve                 → approvePost assigns next free PUBLISH_SLOTS time → SCHEDULED
publish-due (*/5 cron)    → enqueue publish for due posts (singletonKey per post)
publish {postId}          → Threads container → wait FINISHED → threads_publish
publish-chain {postId}    → after the main post: publish post_parts 2..3 in order, each a reply to the previous part
chain-alert {postId, error} → Telegram alert + retry button for finally failed parts (retries Telegram outages)
refresh-token (daily)     → refresh the Threads long-lived token (60 days) near expiry
review-maintenance (hourly) → expire PENDING_REVIEW drafts untouched 48h (EXPIRED) + one "expires within 24h" warning per touch (`expiry_warned_at`, migration `017`; set only after the send, never bumps `updated_at`) + 09/18h reminders + re-enqueue review (as `ifUnsent` jobs, which send only if the draft still has no review message, because the standard-policy review queue cannot drop duplicates) for PENDING_REVIEW drafts without a review message for 10+ min (a crash between the commit and the review enqueue in generate / revive / digest)
collect-insights (daily 05:00) → snapshot Threads insights of recent published posts (post_insights)
weekly-report (Mon 09:00) → collect fresh insights, then send the weekly report to Telegram (also /report)
poll-replies (*/5 cron)   → new Threads replies on posts published <48h ago → Telegram (src/pipeline/replies.ts)
revive-check (/revive)    → judge EXPIRED news drafts evergreen/stale (one LLM call) → list with ♻️ buttons
revive {postId}           → rewrite time-bound wording and convert to the current 반말 voice → EXPIRED → PENDING_REVIEW (origin revived) → review queue
weekly-digest (Sun 18:00, /digest) → fold up to 3 stale EXPIRED drafts into one chain (origin digest) → review queue
```

Key design points that span several files:
- **The `posts` row is the source of truth for publishing, not the job.** `publishPost` claims a row with an atomic `UPDATE … status='PUBLISHING', attempts = attempts + 1, claim_seq = claim_seq + 1`. The new `claim_seq` is the claim's ownership token, and every later write is conditioned on `status='PUBLISHING' and claim_seq = token`. `attempts` is not the token because `publish-now` resets it. A worker that lost its claim to the stale-row sweep therefore writes nothing and never publishes (`LostClaimError`). It saves `container_id` before publishing and re-checks ownership right before `threads_publish`; that check doubles as a heartbeat. `driveContainer` reuses an existing container and treats `PUBLISHED` as done, so retries never double-post. `posts.container_fingerprint` (`012`) hashes the content the container was made for; if the draft changed since (un-scheduled and edited after a failed attempt), the old container only counts when already `PUBLISHED`, otherwise a new one is created (`reuse: false`). On failure, `decideAfterFailure` re-checks the container so a lost response does not mark a live post `FAILED`. A partial unique index on `posts.scheduled_at` (`003`) keeps one post per slot. The `publish` queue uses `retryLimit: 0`; retries happen when `publish-due` re-finds the row (failed attempts go back to `SCHEDULED`, then `FAILED` after 3 attempts). Rows stuck in `PUBLISHING` for more than 10 minutes are treated as crashed and resumed.
- **Thread chains.** A chain is the main post (`posts`, part 1) plus 0-2 owner follow-up replies in `post_parts` (idx 2,3, migration `011`). `THREAD_CHAIN_ENABLED` (default false) only gates generation; a post that already has parts is published as a chain regardless. Parts use the same claim model as posts (`claim_seq` token, `container_id` saved before publishing, ownership re-check before `threads_publish`, stale `PUBLISHING` >10 min resumed, 3 attempts then `FAILED`). A lost publish response with an unknown media id is resolved by exact text among our recent `/me/threads` and `/me/replies`, restricted to items after the slot and (for replies) to `replied_to` = the expected parent; an item missing either field, or more than one candidate, counts as unknown (a failed attempt), never a guess. Since only a following part looks up a missing id, `publishChain` also recovers the last published part's id when it ends, and `dueChainPostIds` brings back posts with a published part lacking an id (within the 48h reply window) so its replies get polled. `composeChain` decides link and CTA placement: the source link goes on the last follow-up (else the main post), the topic tag stays on the main post, and `THREAD_CTA_TEXT` is appended by code to the last follow-up only (never to a single post, never LLM-written, dropped at publish time if it no longer fits 500 chars). Failed parts raise a Telegram alert, sent through the retrying `chain-alert` queue, with a `chainretry:<postId>` button that resets them to `PENDING`; `post_parts.alerted_at` is set only after the send, and `publish-due` re-enqueues unalerted failures, so a crash cannot lose the alert. CLI `publish-now` also publishes or resumes the chain (resetting FAILED parts); `publish-due` also re-finds published posts with pending or stale parts. Insights cover the main post only. `pollReplies` also reads replies under published parts; `threads_replies.part_idx` (`013`, null = main post) puts `[n/total]` in the notification.
- **Volume is a fixed count, not a score threshold.** `rank` sends all candidates in one LLM call and keeps the top `DAILY_POST_COUNT`. Unpicked topics become `SKIPPED`, so news does not carry over to the next day.
- **Dedupe is done by the ranker, not embeddings.** Exact URLs are blocked by `topics.url_hash`. For everything else, the rank LLM sees the candidates plus topics used in the last 14 days and returns `duplicate_of`. `resolveDuplicates` drops invalid, self and mutual references before `pickTop`. Embedding dedupe was removed (`002_drop_embedding.sql`): GeekNews Korean summaries and their HN English originals measured only 0.37–0.63 cosine, so no threshold could separate them. `rankCollected` first expires `COLLECTED` topics older than 48h.
- **LLM calls go through `chatJson`** (`src/llm/openrouter.ts`). It sends a JSON schema built from the zod schema and always re-validates the output with zod. Prompts are in Korean and live in `src/pipeline/prompts.ts`.
- **Generation is grounded in the original article** (`src/pipeline/sources.ts`). GeekNews topics are resolved to their original link, and the GeekNews summary is only aux context; `posts.source_url` is the original. HN items add top comments from `topics.discussion_url` as labeled opinions, never facts. Voice is 반말 without a forced closing question, and with a chain the main post is a ~150-char teaser (`CHAIN_MAIN_LIMIT` 200) with the detail in the follow-ups (docs/decisions.md 7-8); `PROMPT_VERSION` (2) is stored in `generation.prompt_version`. `style.ts` appends a style fragment built from approved posts of the current prompt version (owner-edited first: `generation->>'text' <> text`), recent first and last lines and reject reasons (`posts.reject_reason`, chosen via Telegram reason buttons). `draftPost` shortens once when the model exceeds 500 chars, because providers do not enforce maxLength. Readability + linkedom extract the body; a bot-check interstitial (Anubis, Cloudflare challenge; `isBotChallenge`, matched on markup only those pages have) counts as unreadable, so the GeekNews/feed summary is used instead. If no body can be read, the topic is skipped (`SkipTopicError`, not retried). Transient fetch failures (429/5xx/timeouts, `TransientFetchError`) are retried instead. An initial generate reuses an existing draft and never overwrites one (`on conflict do nothing`). Regeneration goes through `enqueueRegeneration`, which bumps `posts.regen_seq`. The rewrite is applied only if that seq is still the latest and the post is PENDING_REVIEW, so a retried older request cannot clobber a newer result. Jobs on the legacy `generate` queue are forwarded to `generate-v2`. The source URL goes in `link_attachment`, never in the post text.
- **Threads access goes through the `ThreadsApi` interface.** When `THREADS_DRY_RUN=true`, `getThreadsApi()` returns `DryRunThreadsClient`. The token is seeded from env into `platform_accounts` on first use; after that, the DB copy is authoritative.
- **Telegram review.** Buttons and replies act only on the post's current `review_message_id` while it is `PENDING_REVIEW` and `review_revision = revision`. Every text change bumps `revision`, and approval passes the revision the reviewer saw to `approvePost`. `sendForReview` registers a message only if the revision it displays is still current. Sending a new review message strips the previous message's keyboard. Replying to a review message with `수정: <text>` (or `수정1:`) replaces the draft verbatim; for a chain, `수정2:`/`수정3:` replace a follow-up and `삭제2`/`삭제3` delete one (renumbered), and the single message shows [1/3] [2/3] [3/3] with char counts. Any other reply is treated as feedback and triggers regeneration. The bot ignores every chat except `TELEGRAM_CHAT_ID`; `/start` prints the chat id. `/status` shows pipeline state (`src/pipeline/status.ts`). `/add <url> [note]` creates a manual topic whose `topics.note` (the owner's opinion) becomes the post's angle, but never a source of facts. Commands must be registered before the `message:text` handler, which ends the middleware chain for non-reply text. **Threads reply notifications:** `pollReplies` stores new replies in `threads_replies` (reply id is the PK, so only unseen ones are notified) and sends each to Telegram, saving `telegram_message_id`. A Telegram reply to such a message is handled by `answerReply` BEFORE the review-reply logic: it claims `answer_state` null→ANSWERING atomically (one answer per reply) and posts a `reply_to_id` text post through `driveContainer`, saving `answer_container_id` first. On failure the container is re-checked: PUBLISHED means answered (lost response), a known non-publish releases the claim, an unknown outcome keeps it until it goes stale (10 min) and the next attempt reconciles. Notify claims (`notify_claimed_at`) expire the same way; `notified_at` is set only after the message id is saved. Replies are read newest first (first page only). Needs the `threads_read_replies` / `threads_manage_replies` scopes. Without `TELEGRAM_BOT_TOKEN`, review falls back to console output plus the CLI.
- **After approval**, the confirmation message has `unsched:<id>:<epoch>` / `pubnow:<id>:<epoch>` buttons. They are bound to that exact `scheduled_at`. Un-scheduling bumps `revision` and re-sends review. Publish-now only moves `scheduled_at` to now and still goes through the sweep and claim.
- **Expired drafts get a second life** (decision 14, migration `016`). `posts.origin` is `news` / `revived` / `digest` and shows as a label on the review message. `/revive` (`src/pipeline/revive*.ts`) judges EXPIRED news drafts from the last 30 days once (`revive_verdict` evergreen/stale); `♻️` revives one with a single conditional UPDATE (still EXPIRED, not revived, not digested), rewriting time-bound wording into the current voice (facts and numbers kept; `prompt_version` 2) and setting `generation.text` to the new text (original in `generation.revived.from_text`) so `style.ts` does not learn the LLM's rewrite as an owner edit. The weekly digest (`src/pipeline/digest*.ts`) takes up to 3 not-evergreen EXPIRED drafts from the last 10 days by topic score, builds one chain in one transaction (a MANUAL topic, the post, its parts) and claims the members via `digest_post_id` (fewer than 2 claimed → rollback). Each digest part carries its own source as `post_parts.link_url`; when any part has one, `composeChain` gives the main post `source_url` and every part its own link instead of the last-part rule. Regeneration of a digest post (🔁, feedback) is routed in `jobs.ts` to `regenerateDigest`. Both send the review through the retrying `review` queue, never inline, because a retried job could not redo the claim; a lost enqueue is recovered by the hourly `review-maintenance` sweep (`loadUnsentReviews`). `applyReviewEdit` (`수정2:`/`삭제2`) moves each part's `link_url` with its part.
- **Final-failure alerts.** `alertOnFinalFailure` in `jobs.ts` notifies Telegram when the daily, generate or review job throws on its last attempt. The retry-limit constants there are shared with `createQueue`.

Campaign pipeline (`src/campaigns/`, migration `014`), same Postgres and pg-boss. Queues are defined in `src/campaigns/jobs.ts` (`CQ`); one cloud worker handles all of them:

```
gift-collect (GIFT_COLLECT_CRON, default 0 9,15,21) → public list (GIFT_TRIAL_PAGE_ID) → upsert campaigns COLLECTED → rank → send campaign-card per pick
campaign-card {campaignId}   → Telegram photo card (competition, D-n, buttons: open in 카카오톡 / 신청함 / 패스) → PENDING_REVIEW
  신청함 → APPLIED → 선정 / 미선정 → SELECTED / NOT_SELECTED
review-draft {campaignId, feedback?, seq} (singleton per campaign) → draft + control message → DRAFT_REVIEW; 리뷰 올림 → POSTED
campaign-maintenance (hourly) → expire cards past the apply deadline (EXPIRED), reminders 09-21h only
musinsa-collect (MUSINSA_COLLECT_CRON, default 0 10,16,22) → public preuser list → upsert campaigns (source musinsa) + detail of new rows → rank → send campaign-card per pick
campaign-rank                → legacy: rank every COLLECTED campaign (nothing enqueues it any more; both collectors rank themselves)
```

- **The `campaigns` row is the source of truth**, and every transition is a conditional `UPDATE … where status = … and revision = …` that reports whether it applied, so stale buttons and double presses change nothing. Statuses: COLLECTED → SKIPPED | SHORTLISTED → PENDING_REVIEW → REJECTED | EXPIRED | APPLIED → SELECTED | NOT_SELECTED → DRAFT_REVIEW → POSTED. Nothing external happens in these transitions: the owner applies and posts the review by hand (Kakao: the KakaoTalk mobile app, desktop redirects to a mobile-only page; Musinsa: from the card link, on a PC) and records it with a button. `campaigns.source` is `kakao-gift` or `musinsa`; `CAMPAIGN_SOURCES` in `types.ts` holds each source's label, where it is applied (`applyOn`) and the review place used in prompts.
- **Gift price** (`fetchGiftProductPrice`, `fillGiftPrices`): after the upsert, new and still-COLLECTED gift rows without `detail.price` get `{ basic, selling }` from the public product API `GET /a/product-detail/v3/products/<productId>` (`price.basicPrice` / `price.sellingPrice`), 300 ms apart, at most 150 per run; a failure is logged, stamps `detail.priceTriedAt` (no retry for 6 h) and never fails the collection. Ranking leaves gift rows whose price was never tried COLLECTED (`awaitingPrice` in `rank.ts`), so rows past the cap are ranked in a later run with their price instead of once without it. The gift upsert merges `detail` (`campaigns.detail || excluded.detail`) so stored prices survive. `campaignPrice(c)` / `campaignPriceInfo(c)` in `types.ts` give the list price (gift `detail.price.basic`, Musinsa representative `normalPrice`) for the rule, the rank prompt (higher-priced products score higher, all else equal), the gift card (`정가 49,000원`) and the dashboard (`price` in `/api/campaigns` rows).
- **Collection** (`gift.ts`, `collect.ts`): the public JSON list of gift.kakao.com page `GIFT_TRIAL_PAGE_ID` (default 33325): first page 50 items, then `collections?page=2..` (size 24) until `isLast`/empty items, 400ms apart, 475 items on 2026-10-18 (19 pages, hard cap 40). A failure on page 1 throws; a later page logs and keeps what was read. The upsert (`on conflict (source, external_id)`) refreshes list fields, `detail` and `last_seen_at` only; status, score, owner fields and `updated_at` are never touched. `apply_deadline` is an ESTIMATE: the end of KST day `today + remainingDays` (the real cut-off hour and rounding are unknown), shown as `(추정)`. The detail page needs login, so everything is judged from public list fields: title, brand, image, recruit/application counts, remaining days.
- **Musinsa collection** (`musinsa.ts`, `collect.ts`, `http.ts`): the 체험단 list shown on musinsa.com/preuser/main is a **public JSON API, no login**: `GET https://www.musinsa.com/preuser/api/v1/event/events?page=N&size=100` (1-based pages; 100 is the largest accepted size, a larger one is capped; `hasNext` false on the last page, the page after it answers an empty `content`; 352 items = 4 pages on 2026-10-19), `/event/count` and `/event/events/:id` (detail). Do not confuse it with `influencer.musinsa.com/api2/mcmp/...` (login-only creator campaigns, a different id space), which an earlier version read by mistake (migration `018` removes those rows). `fetchMusinsaList` works like the gift list: plain `fetch` through the shared `makeGetJson` (`http.ts`: 15s timeout, one retry on 429/5xx/network), zod envelopes, a first-page failure throws, a later-page failure logs and keeps what was read, 20-page cap, 300ms apart; only `state = OPEN` items are kept. `collectMusinsaCampaigns` upserts like the gift collector: `external_id` = event id, link `https://www.musinsa.com/preuser/events/<id>`, title = `name`, brand = `brand.name`, `recruit_count` / `application_count` = `recruitmentCount` / `applicantsCount`, `product_id` = representative product `uniqueId`, `apply_deadline` = end (23:59:59.999) of the KST day `endDate` (exact day, so not shown as an estimate; the cut-off hour inside that day is unknown), `detail` = the list item. On conflict the list item is merged over the stored `detail` (`||`), so detail-only fields survive. Only for **newly created rows** the event detail is fetched (300ms apart; a failure is logged and skipped, never fails the collection) and `eventCategory`, `winnerDrawDate`, `deliveryDate`, `reviewStartDate`, `reviewEndDate`, `minimumMemberLevel` and `optionNames` are merged into `detail`. `musinsaFacts` (`types.ts`) reads price (representative product normal price, sale price only when lower), goods count (`products.length`), category (`musinsaCategoryLabel`, ids from `/event/filters`) and the dates. Applying needs the owner's login and 무신사 프리유저 registration (at least one 스냅 posted), so the owner applies by hand on a PC from the card link and records it with `✅ 신청함`. Later phase: Aside (the owner's logged-in browser) for auto-apply; the removed Aside client is in git history.
- **One worker:** `src/worker.ts` always runs the whole thing (migrations, Telegram polling, all queues including `musinsa-collect`, dashboard). There is no local worker role any more.
- **Ranking** (`rank.ts`, `prompts.ts`): `ruleSkipReason` first skips by `excludeKeywords`, `excludeBrands`, `maxCompetition` (optional), `minPriceWon` (optional; skips a known list price below it as `가격 낮음: 14,900원`, an unknown price passes) and closed deadline (`SKIPPED` + `skip_reason`). The rest are split by source (`rankSystem(source)` differs; Musinsa candidates add category, price and goods count to the same competition line) and go to `chatJson` (`LLM_RANK_MODEL`) in batches of 60 with the profile and the last 10 applied/rejected titles (with reject reasons). The top `CAMPAIGN_DAILY_MAX` **per source** per KST day (counted from `shortlisted_at`, migration `015`; not `updated_at`, which hourly maintenance also bumps when it expires never-picked rows) become SHORTLISTED; after ranking, cards are sent for every SHORTLISTED row, not just this run's picks, so a pick whose card was never queued is recovered; scored leftovers are SKIPPED; campaigns the model did not score, or all of them once the quota is used, stay COLLECTED for the next run.
- **Telegram card** (`telegram.ts`, `tg.ts`): photo card (`image_url`, caption <= 1024) with competition and D-n, buttons one per row: `📱 카카오톡에서 열기` (URL; the source label is 카카오톡 for `kakao-gift`; with `PUBLIC_BASE_URL` and the dashboard enabled it points to `${PUBLIC_BASE_URL}/go/gift/<id>`, otherwise straight to gift.kakao.com; the hand-off is a public hand-off page that opens KakaoTalk's in-app browser via `kakaotalk://inappbrowser?url=…`, because the gift page only works logged in inside KakaoTalk; `📱 무신사 앱에서 열기` for Musinsa → `https://link.musinsa.com/preuser/events/<id>` (`musinsaAppUrl`), an iOS universal link into the Musinsa app that redirects to the www page without the app or on a PC, while `campaigns.url` stays the www URL; the Musinsa card also shows category, list price (→ sale price), goods count, the announcement date (발표) and the review period (리뷰), and tells the owner to apply in the app or on a PC), `✅ 신청함`, `🙅 패스` (reason picker: category / competition / brand / other, with cancel). Callbacks are `camp:<action>:<id>:<revision>[:<arg>]` and `rev:<action>:<id>:<revision>` (`callbacks.ts`); card buttons are bound to `review_message_id` and `review_revision = revision` while PENDING_REVIEW, while result buttons (`🎉 선정` / `😢 미선정`, which appear after `✅`) and `📝 리뷰 초안 쓰기` are gated by status alone (revision 0). `markCardSent` registers a card only if its revision is current, then the previous card loses its keyboard. `/camps` lists active campaigns by stage; `/due <id> <date>` (M/D, M-D, M.D or YYYY-MM-DD, end of that KST day) sets `review_deadline`. Handlers are registered through the `extend` hook of `createReviewer`, before the `message:text` handler.
- **Reminders** (`reminders.ts`, run by `campaign-maintenance` between 09 and 21 KST): `result-check` (APPLIED, a day after the estimated apply deadline, with 선정/미선정 buttons), `due-missing` (SELECTED a day without a review deadline; `markResult` already fills `review_deadline` with the end of the KST day `detail.reviewEndDate` for a selected Musinsa campaign when none is set, and `/due` still overrides it), and `review-d3/d1/d0` by calendar day to `review_deadline` (only the most specific due kind, never a stale one). Each is claimed by inserting a `campaign_reminders` row first (`on conflict do nothing`) and deleted again if the send throws.
- **Review draft** (`review-draft.ts`, `review-telegram.ts`): `📝 리뷰 초안 쓰기` (SELECTED or DRAFT_REVIEW) sends an intake message and stores its id in `intake_message_id`; a reply with the owner's memo is saved in `memo` and enqueues `review-draft`. `regen_seq` is bumped at request time (`requestDraftRegeneration`) and the write is applied only if it is still the latest and the memo is unchanged. The draft is grounded in the memo only (no invented experience, numbers or specs), kept within `review.minChars`..`maxChars` (shorten/expand once, then cut at a sentence). The review place named in the prompt comes from the source (카카오톡 선물하기 상품 리뷰 / 무신사 상품 후기). Two messages go out: the draft alone (long-press copy) and a control message with `🔁 다시 쓰기` / `✅ 리뷰 올림`; replying `수정: <text>` to the control message replaces the draft verbatim, any other reply is feedback and regenerates, and each text change bumps `revision` so old buttons die. `✅ 리뷰 올림` → POSTED.
- **Disclosure is code, not LLM:** `disclosure` from `config/campaign-profile.json` (`CAMPAIGN_PROFILE_PATH`) is prepended by `composeReview` to every draft (and to `수정:` replacements) and its length is reserved within `maxChars`; the prompt tells the model not to write one. The profile has no address or phone (Kakao has them).
- **Queues and failures:** `gift-collect` is a `stately` queue (retryLimit 1), `campaign-card` `exclusive` (3), `review-draft` `singleton` (2, backoff), `campaign-maintenance` `stately` (0), `musinsa-collect` `stately` (1) and `campaign-rank` `stately` (1). `alertOnFinalFailure` in `campaigns/jobs.ts` (reusing `formatFinalFailure` / `isFinalAttempt`) sends a Telegram alert on the last attempt. `src/campaigns/tg.ts` sends with `Api` directly, so the CLI can send cards too; without a bot token it logs.
- **Web dashboard** (`src/web/`, `docs/dashboard.md`): the data API (`/api/overview`, `/api/campaigns`, ...) is GET/HEAD only. **Campaign operations (admin console stage 2, migration `020`, `src/web/campaign-actions.ts`, `src/campaigns/actions.ts`):** `POST /api/campaigns/:id/<apply|reject|result|deadline|memo|regenerate|draft|posted>` write campaign state through the same conditional functions the Telegram buttons call (`markApplied`, `rejectCampaign`, `markResult`, `setReviewDeadline`, `saveMemo`, `replaceDraftGuarded`, `markPosted(…, { control: false })`), on the `revision` / `status` the page displayed; a transition that does not apply is a 409 `{ error, stale: true }` and the app refetches. Memo and regenerate only call `enqueueReviewDraft` (the injected `enqueueDraft` of `startDashboard()`), never the LLM; "draft pending" is `regen_seq > draft_seq` (`draft_seq` = the `regen_seq` the draft was written for, set by `generateReviewDraft` and `replaceDraftGuarded`). After a success the Telegram card or control message is left as the equivalent press would (best effort, reported as `telegramSynced`); the message texts are shared with the bot (`appliedText`, `passedText`, ...). Session + same-origin + `X-CSRF-Token` are checked by `authorizeWrite` in `server.ts` (also used by logout), every call is audited as `campaign.<action>` in `admin_actions` (memo and draft text are never logged), and action bodies may be 16KB (the auth routes keep 4KB). The cloud worker starts it with `startDashboard()` only when Telegram is configured (`dashboardEnabled()` in `config.ts`), listening on `PORT` (Railway) or 8080. **Login (admin console stage 1, migration `019`, `src/web/auth.ts`):** `POST /api/auth/code` sends a 6-digit one-time code to `TELEGRAM_CHAT_ID` (5 min, single use, 5 wrong tries lock it, 1 request/min and 5/hour, all serialized by an advisory lock); `POST /api/auth/login` opens a 30-day session: a random token in the `ca_session` cookie (`HttpOnly; Secure; SameSite=Strict`), only its sha256 in `admin_sessions`; the CSRF token is derived from the session token and returned by `GET /api/auth/session`. Every POST must be same-origin JSON (Origin vs Host / X-Forwarded-Host / `PUBLIC_BASE_URL`, `Sec-Fetch-Site`), logout routes also need `X-CSRF-Token`. Auth events go to the `admin_actions` audit log; logins, locks and rate-limit hits alert Telegram. `/api/*` data without a session is a JSON 401. `/healthz`, `GET/HEAD /go/gift/:id` and the static app shell (no data) need no session; the hand-off accepts only a 24-char lowercase hex id and always points at the fixed `https://gift.kakao.com/giftbox/trial-campaign/<id>`, never at a user-supplied URL. The UI is the React + Vite + Tailwind + shadcn/ui app in `web/` (its own package and lockfile; `npm run build:web` → `web/dist`, also run by the root `build` script and CI). The server serves `web/dist` (hashed `/assets/*` immutable, `index.html` no-store for every other non-API path, traversal rejected) plus the JSON API in `src/web/api.ts`, whose shapes are the contract in `src/web/api-types.ts` (imported by the app with `import type` only). Without a build the app routes answer 503 (the server-rendered pages were removed with the login change). The React app gets `script-src 'self'`; the root vitest excludes `web/**` (`npm run test:web` runs the app's own jsdom tests). The campaign list has a `?source=` filter, the overview and `/status` count campaigns per source, and thumbnails may also come from `image.msscdn.net` (`IMAGE_HOSTS` in `server.ts`, the CSP allowlist).

## Environment notes

- **DB SSL:** `DATABASE_SSL` (default true) controls `dbSsl` in `src/db/pool.ts`, shared with pg-boss. Set it to false only for local/CI Postgres.
- **Supabase:** use the **session pooler** URL (`aws-0-ap-northeast-2.pooler.supabase.com:5432`). The direct `db.*.supabase.co` host is IPv6-only. Transaction mode (port 6543) does not suit a long-running pg-boss worker.
- **pg types:** `pg` is configured in `src/db/pool.ts` to parse `int8`/`numeric` as JS numbers.
- **Threads API:** host `graph.threads.net/v1.0`. Posts have a 500-character limit, at most 5 links, and 250 posts per 24h. The Meta app runs in development mode with the owner as a Threads tester, so no App Review is needed. Keep the profile public; private-profile grants expire after 90 days.
- **hnrss.org** returns HTTP 429 when polled repeatedly in a short window. `collectAll` isolates per-feed failures.
