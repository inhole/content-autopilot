# 설계 결정

처음 설계 초안(n8n + Threads/Instagram/YouTube 동시 자동화)을 검토한 뒤 바꾼 것들이다. 결정마다 이유와 다시 검토할 조건을 같이 적는다.

## 1. MVP는 Threads만 한다

- **이유**
  - 영상 파이프라인(TTS, 렌더링, 자막 싱크, 저장소)이 원래 설계에서 가장 어렵고 비싼 부분이었는데, 이걸 통째로 뺄 수 있다.
  - YouTube는 검증 안 된 API 프로젝트로 업로드하면 비공개로 고정된다. 감사를 통과하려면 몇 주가 걸린다.
  - Google OAuth는 동의 화면이 Testing 상태면 refresh token이 7일 만에 만료된다.
  - Meta 앱은 개발 모드에서 본인을 테스터로 등록하면 심사 없이 바로 쓸 수 있다.
  - Threads는 반응이 몇 시간 안에 와서, 주제와 말투를 고치는 주기가 가장 짧다.
- **다시 검토할 때:** Threads 발행이 안정적으로 돌고, 어떤 주제가 반응이 좋은지 데이터가 쌓였을 때 Instagram Reels / YouTube Shorts를 붙인다. `posts.platform` 컬럼이 이미 있어서 확장할 수 있다.

## 2. n8n을 쓰지 않는다

- **이유**
  - 원래 설계도 n8n에게 순서만 맡기고 실제 작업은 API로 넘기는 구조라, n8n이 하는 일은 사실상 cron이었다.
  - 워크플로우가 git 밖(n8n DB)에 있어서 버전 관리와 테스트가 어렵다.
  - 로직이 두 군데로 나뉘고 운영할 서버가 하나 더 늘어난다.
- **대신 쓰는 것:** pg-boss. cron 스케줄, 재시도와 backoff, singleton/exclusive 정책을 이미 쓰고 있는 Postgres 위에서 처리하므로 서버를 추가하지 않아도 된다.

## 3. 콘텐츠는 뉴스 수집을 중심으로 만든다

- **이유:** 사람이 들이는 시간을 최소로 하는 것이 목표다.
- **리스크:** 남의 글을 모아 재가공한 콘텐츠는 노출이 줄 수 있다. Instagram이 원본 콘텐츠를 우대하고 있고, YouTube도 대량 생산한 콘텐츠의 수익화를 제한한다.
- **리스크를 줄이는 장치** (생성 프롬프트에 강제)
  - 기사 본문에 있는 사실만 쓴다.
  - 자기 말로 요약한다.
  - 개발자 관점의 해석을 하나 이상 넣는다.
  - 출처 링크를 붙인다.
- **다시 검토할 때:** 도달이 계속 낮으면, 내가 직접 쓴 한 줄 의견을 입력하는 방식을 섞는다.
- **추가된 장치:** Telegram `/add <url> [한 줄 의견]`으로 휴대폰에서 바로 기사와 의견을 넣을 수 있다. 의견(`topics.note`)이 글의 관점이 된다.

## 4. 점수 기준이 아니라 고정 개수로 고른다

- **이유:** LLM이 매기는 0~10점은 기준이 일정하지 않다. "7.5점 이상" 같은 기준을 쓰면 날마다 제작 수가 0개가 되기도 하고 10개가 되기도 한다. 그래서 하루 상위 N개를 고른다.
- 원래 설계에 있던 "논란성 가산점"은 뺐다.

## 5. 승인은 Telegram 봇으로 받는다

- **이유:** 이동 중에 승인하는 사용 방식에 맞고, 웹 관리자 화면을 만들지 않아도 된다.
- 승인 단계는 없애지 않는다. AI가 틀린 사실을 내 이름으로 발행하는 걸 막는 유일한 장치다.
- **나중에:** 품질이 안정되면 조건부 자동 승인을 검토한다.

## 6. 성과 기반 자동 개선은 미룬다

- **이유:** 표본이 너무 작다. 하루 3개면 한 달에 90개라, 상위와 하위를 비교해도 통계적으로 거의 노이즈다. 이걸로 프롬프트를 자동으로 바꾸면 방향이 엉뚱하게 흐를 수 있다.
- **계획:** Threads insights를 수집하는 기능을 먼저 붙이고, 주간 리포트를 사람이 보고 판단한다.

## 7. 글은 반말로, 질문을 강요하지 않고 사람이 쓴 것처럼 쓴다

- **이유(2026-10-18, 최초):** Threads는 좋아요보다 답글을 강한 노출 신호로 쓴다고 알려져 있어서, 처음에는 모든 글을 독자가 답할 수 있는 질문으로 끝내게 했다. 한국 Threads는 처음 보는 사람끼리도 반말로 수다 떨듯 얘기하는 곳이라('스레드체'), 기사체와 존댓말 글은 피드에서 정보 퍼 나르기로 읽힌다.
- **바꾼 이유(2026-10-21):** 실제로 올려 보니 두 가지가 맞지 않았다.
  - 모든 글이 "다들 ~함?"으로 끝나 공식처럼 보였고, 성과도 없었다. 조회 39~77, 좋아요 0, 답글 0~1이었다. 억지 질문이 답글을 부르지 못했다.
  - 글 전체가 AI가 쓴 것처럼 읽혔다. 훅, 사실 2~3개, "난 ~라고 봄", 질문의 고정된 틀과 "흥미로운 건", "핵심은" 같은 표현 때문이다. 음슴체(`~함`, `~했음`)도 직접 써 보니 어색했다.
- **규칙 (`GENERATE_SYSTEM`):**
  - **말투는 반말**이다(`~야`, `~어/아`, `~더라`, `~거든`, `~네`, `~지`, 전해 들은 얘기는 `~대`, `~ㄴ 듯`). 음슴체, 기사체, 존댓말은 쓰지 않는다. 마침표 없이 한 줄에 한 문장은 그대로다.
  - **마지막 질문을 강요하지 않는다.** 내 생각 한 줄, 가벼운 반응, 사실로 끝내도 된다. 질문은 정말 자연스러울 때만 드물게 쓴다. "어떻게 생각해?", "댓글로 알려줘", 좋아요·팔로우·리포스트 요청은 여전히 금지다(노출이 낮아진다). 이 금지는 LLM이 쓴 글에만 적용된다. 연결 글의 고정 CTA는 코드가 붙이는 예외다(결정 8). 선정(`RANK_SYSTEM`)의 "대화 가능성" 기준은 그대로다.
  - **사람이 쓴 글처럼.** 고정된 틀을 반복하지 않고 시작과 끝을 바꾼다. 균형 잡힌 요약보다 강한 반응 하나를 앞세운다. 숫자는 글당 1~2개. "다만 ~" 반론, "흥미로운 건", "와닿았어", "핵심은", "결론적으로", "~라는 점에서", "시사하는", "주목할 만한", 대시, 콜론 목록, 전해 들은 어미(`~대`)의 줄마다 반복은 쓰지 않는다.
  - 시점은 기자가 아니라 "소식을 먼저 본 개발자"다. 과장·낚시, 비속어, ㅋㅋ, Threads 은어, 훈계는 쓰지 않는다. 겪지 않은 경험은 작성자 의견에 있을 때만 쓴다.
- **문체 학습(`style.ts`):** 예시는 `generation.prompt_version >= 2`(`PROMPT_VERSION`)인 글에서만 가져온다. 옛 글은 음슴체와 질문 마무리라 예시로 쓰면 초안이 다시 그쪽으로 끌려간다. 최근 첫 줄·마지막 줄은 중복 회피용이라 버전과 상관없이 쓴다. `수정:` 답장으로 고친 글(v2 이상)이 여전히 1순위다. 재활용(revive)한 글은 새 말투로 다시 쓰므로 v2로 기록하고, 주간 묶음 글도 같다.
- **링크:** Adam Mosseri가 외부 링크의 노출 불이익을 거둬들였다고 밝혔으므로, 원문 링크는 지금처럼 `link_attachment`에 둔다.
- **한계:** 외부 가이드와 몇 건의 실제 수치(위 조회·답글)를 근거로 정한 규칙이고 표본이 작다(결정 6). 반말·질문 없음으로 바꾼 뒤 insights로 다시 비교한다. Telegram 봇 안내 문구는 그대로 존댓말이다.

## 8. 연결 글과 고정 CTA

- **이유:** choi.openai 같은 큰 한국 AI 계정이 연결 글(본글 + 작성자 본인의 답글) 형식을 쓴다. 500자 한 글에 사실 요약, 개발자 해석, HN 반응을 다 넣기는 어렵다.
- **결정**
  - 연결 글은 본글(`posts`, 1번째)과 작성자 본인의 답글 0~2개(`post_parts`, idx 2·3)로 이루어진다. 내용이 얇은 주제에는 붙이지 않고 짧은 단독 글을 쓴다.
  - **본글은 짧은 맛보기다(2026-10-21).** 1~3줄, 150자 안팎, 링크 없음. 질문으로 끝낼 필요가 없고 내용을 다 담지 않는다. 코드는 답글이 있으면 본글을 200자(`CHAIN_MAIN_LIMIT`)에 맞춰 한 번 줄인다. 상세는 답글이 맡는다. 첫 번째 답글은 실제로 무슨 일이 있었는지(기사 본문의 사실), 두 번째 답글(선택)은 내 생각과 HN 반응이다. 처음에는 본글에 훅·핵심·질문을 모두 두고 답글이 해석과 보충을 맡았지만, 길고 AI 같아 뒤집었다.
  - 출처 링크는 답글이 있으면 마지막 답글에, 없으면 본글에 붙인다. 주제 태그는 본글에 둔다.
  - 고정 CTA(`THREAD_CTA_TEXT`)는 마지막 답글 끝에만 코드가 붙인다. 글이 하나뿐이면 붙이지 않고, LLM은 쓰지 않는다. 발행할 때 500자에 맞지 않으면 CTA를 뺀다. **2026-10-21: 작성자 결정으로 CTA는 쓰지 않는 것을 권장한다.** `THREAD_CTA_TEXT`를 설정하지 않으면 붙지 않는다(`.env.example`의 예시 값도 뺐다). 기능은 남겨 둔다.
  - `THREAD_CHAIN_ENABLED`(기본 false)는 생성에만 영향을 준다. 이미 답글 조각이 있는 글은 이 값과 관계없이 연결 글로 발행한다.
  - 2~3주는 끈 상태로 돌려 기준선을 만들고, 그다음 켜서 비교한다.
  - insights는 본글만 수집한다. 주간 리포트가 연결 글과 단일 글의 평균 조회·답글을 비교한다.
- **리스크**
  - 결정 7에서 참여 유도 문구를 금지했는데 CTA는 그 예외다. Threads가 참여 유도로 보고 도달을 낮출 수 있다.
  - 답글은 본글이 나간 뒤에 차례로 발행하므로 일부만 올라갈 수 있다. 실패해도 본글은 그대로 남는다.
  - 독자가 답글 조각에 단 답글도 Telegram으로 알린다. 알림에는 `[2/3]`처럼 어느 글에 달렸는지 표시한다(`threads_replies.part_idx`, `013`).
- **다시 검토할 때:** 2~3주씩 두 구간의 insights를 비교한다. 연결 글의 조회·답글이 단일 글보다 낮거나 CTA를 붙인 뒤 도달이 줄면 CTA부터 뺀다. 표본이 작아서(결정 6) 한 구간의 차이만으로 단정하지 않는다.

## 9. 체험단 출처는 카카오 선물하기 공개 목록이다

- **이유**
  - 처음에는 레뷰(revu.net) 공고를 카카오톡 단체방에서 읽고, Aside 브라우저로 신청하고, 네이버 블로그에 임시저장하는 구조로 짰다. 이 가정이 틀렸다. 내가 실제로 하는 체험단은 **카카오톡 선물하기 체험단**이다. 레뷰도 네이버 블로그도 쓰지 않는다.
  - 선물하기 체험단 목록은 gift.kakao.com의 **공개 JSON**이다. 로그인이 필요 없어서 카톡 PC 앱을 UI 자동화로 읽을 이유가 사라졌다. 약관 위험이 큰 카톡 읽기, 로컬 PC 워커, Aside, 네이버 임시저장이 통째로 필요 없어졌다.
  - 큐, 재시도, Telegram 승인, 행 상태 기준, `chatJson`은 이미 이 레포에 있다. 별도 패키지로 나누지 않고 같은 워커에 추가한다. n8n은 여전히 쓰지 않는다(결정 2).
- **결정**
  - 대상은 선물하기 체험단 탭(`GIFT_TRIAL_PAGE_ID`)의 공개 목록 전체다. 워커 하나(Railway)가 `gift-collect`로 하루 3번 읽는다.
  - `campaigns` 행이 상태의 기준이다(`014`). "MVP는 Threads만" 범위가 이 파이프라인만큼 넓어졌다. Threads 쪽 결정은 그대로다.
   - 이전 가정(레뷰, 카톡방, 네이버)은 코드와 문서에서 모두 지웠다. 선물하기에는 Aside를 쓰지 않는다. 무신사 목록도 공개 API라 수집에는 쓰지 않고, 로그인이 필요한 자동 신청을 만들 때만 Aside를 다시 쓸 수 있다(결정 13).
- **다시 검토할 때:** 선물하기 목록 API 형식이 자주 깨지거나 막히면 다른 수집 방법을 본다. 다른 체험단 사이트를 붙일 때는 `campaigns.source`가 이미 있어서 확장할 수 있다. 무신사 프리유저는 `source = musinsa`로 붙였다([결정 13](#13-무신사는-로그인이-필요해-이-pc의-aside로만-읽는다)).

## 10. 신청과 리뷰는 사람이 하고 버튼으로 기록한다

- **이유**
  - 선물하기 체험단의 신청과 리뷰 작성은 모바일 전용이다. PC에서 열면 모바일 전용 안내 페이지로 넘어간다. 코드가 흉내 낼 데스크톱 경로가 없다.
  - 신청 폼에는 옵션 선택과 배송지뿐이라 자동화로 얻을 것이 적다. 반면 잘못 신청하면 되돌리기 어렵다.
  - 리뷰는 내 이름으로 나가는 글이다. 써보지 않은 경험을 지어낸 글이 올라가면 안 된다.
- **결정**
  - 신청: 카드의 `📱 카카오톡에서 열기`로 폰 카톡에서 열어 내가 신청하고, `✅ 신청함`으로 기록한다. 결과는 `🎉 선정` / `😢 미선정`으로 기록한다. 리뷰 기한은 `/due`로 알린다.
  - 리뷰: 내가 쓴 사용 메모를 답장하면 LLM이 초안을 쓴다. 초안은 메모에 있는 내용만 근거로 하고(결정 3의 "본문에 있는 사실만"과 같은 원칙), 복사하기 쉽게 초안만 담은 메시지를 따로 보낸다. 내가 선물하기에 직접 올리고 `✅ 리뷰 올림`으로 기록한다.
   - 무신사 프리유저도 같다. 카드의 `💻 무신사에서 열기`로 PC에서 열어 신청하고 `✅ 신청함`으로 기록한다(결정 13).
  - 코드는 외부에 아무것도 신청하거나 올리지 않는다. 카드는 출처마다 하루 `CAMPAIGN_DAILY_MAX`(기본 5)개까지만 보낸다.
  - 기록이 빠지면 안 되므로 마감 지난 신청의 결과 확인(`result-check`), 기한 누락(`due-missing`), 리뷰 마감 D-3·D-1·D-day 리마인더를 보낸다(09~21시만).
- **다시 검토할 때:** 선물하기가 PC 신청이나 공식 경로를 열면 신청 보조를 검토한다. 리뷰 게시는 자동화하지 않는다. 기록 버튼을 자주 빼먹으면 리마인더 문구나 빈도를 조정한다.

## 11. 선별은 공개 정보만으로 한다

- **이유:** 체험단 상세 페이지는 로그인이 필요하다. 목록이 주는 제목, 브랜드, 이미지, 모집·신청 인원, 남은 일수만 로그인 없이 안정적으로 얻을 수 있다.
- **결정**
  - 코드가 먼저 규칙으로 거른다: 제외 키워드·브랜드, 경쟁률 상한(`maxCompetition`, 선택), 최소 정가(`minPriceWon`, 선택, 가격을 모르면 거르지 않음), 마감 지남.
  - 남은 후보는 LLM이 0~10점으로 매긴다. 60건씩 나눠 부르고, 프롬프트에는 프로필과 최근 신청·패스한 체험단(패스 사유 포함)이 들어간다. 후보에 적힌 정보 밖의 제품 특성은 추측하지 않게 한다.
  - 출처마다 하루 상위 `CAMPAIGN_DAILY_MAX`개만 카드로 보낸다. 점수 문턱이 아니라 고정 개수다(결정 4와 같은 이유). 출처가 다르면 후보 모양(인원 대 정가·리뷰 형식)과 프롬프트가 달라서 LLM 호출과 한도를 따로 센다.
  - **신청 마감은 남은 일수로 추정한 값이다.** 오늘(KST)에 남은 일수를 더한 날의 끝을 마감으로 두고, 카드와 대시보드에 `(추정)`이라고 적는다. 실제 마감 시각과 일수 계산 방식은 아직 확인하지 못했다.
- **다시 검토할 때:** 마감 추정이 자주 틀리면(마감된 카드가 오거나 `EXPIRED`가 너무 일찍 된다) 남은 일수의 의미를 실측해 계산을 고친다. 선별 품질이 낮으면 패스 사유를 모아 프롬프트와 프로필 규칙을 고친다. 상세 정보를 얻을 합법적인 경로가 생기면 선별 입력을 늘린다.

## 12. 광고 표기는 코드가 강제한다

- **이유:** 공정위 추천·보증 심사지침은 경제적 대가를 받았다는 사실을 글 첫머리에 밝히도록 한다. LLM에게 맡기면 빠지거나 문구가 흔들릴 수 있다. 결정 8의 CTA를 코드가 붙이는 것과 같은 방식이다.
- **결정:** 프로필(`config/campaign-profile.json`)의 `disclosure` 문구를 모든 리뷰 초안 맨 앞에 코드가 붙인다. 프롬프트는 모델에게 표기를 쓰지 말라고 하고, 모델이 비슷한 줄을 써도 중복해서 붙이지 않는다. `수정:` 답장으로 본문을 바꿔도 맨 앞 표기는 유지된다. 표기 줄의 길이는 최대 글자 수에서 미리 뺀다.
- **다시 검토할 때:** 지침이나 선물하기의 표기 요구가 바뀌면 `disclosure` 문구만 고친다. 프로필에서 `disclosure`를 빼면 표기가 사라지므로, 체험단 리뷰에서는 빼지 않는다.

## 13. 무신사 체험단 목록은 공개 API라 클라우드에서 읽는다

- **이유**
  - 무신사 체험단 목록(`musinsa.com/preuser/main`)은 로그인 없이 읽히는 공개 JSON이다(`/preuser/api/v1/event/events?page=1&size=100`, 상세는 `/event/events/:id`). 2026-10-19에 352건, 4페이지를 확인했다. 선물하기와 같은 방식으로 클라우드 워커가 읽는다.
  - 처음에는 `influencer.musinsa.com/api2/mcmp/v2/recruitment-campaigns`를 체험단 목록으로 잘못 읽었다. 이것은 로그인이 필요한 다른 시스템(크리에이터 캠페인)이고 ID 체계도 달라서(389xx), 카드 링크 `preuser/events/<id>`가 실제 체험단과 맞지 않았다. 그래서 이 PC의 Aside와 로컬 워커까지 만들었지만 모두 필요 없었다.
  - 공개 API에는 모집 인원과 신청자 수가 있어서 선물하기처럼 경쟁률을 계산할 수 있고, 상세에는 발표일과 리뷰 기간이 있다.
  - 신청, 내 신청 내역 API는 프리유저 가입이 있어야 쓸 수 있다. 가입은 스냅을 한 번이라도 올려야 한다(`MCMP_001_006 작성한 스냅이 있는 회원만 신청할 수 있습니다`). 지금은 자동 신청을 만들어도 쓸 수 없다.
- **결정**
  - 무신사 목록 수집은 클라우드 워커의 `musinsa-collect`가 한다(`MUSINSA_COLLECT_CRON`). 선물하기와 같이 수집, 선별, 카드 전송까지 한 번에 이어진다. 로컬 워커(`WORKER_ROLE`), Aside 클라이언트, 로그인 알림은 지웠다. 이 PC에 예전에 등록한 예약 작업이 있으면 지워도 된다.
  - 새로 들어온 공고만 상세를 읽어 품목, 발표일, 리뷰 기간, 옵션 이름을 `detail`에 보관한다. 상세 읽기가 실패해도 수집은 실패하지 않는다. 선정으로 기록하면 상세의 리뷰 마감일(`reviewEndDate`)이 `review_deadline`으로 들어가고, `/due`로 바꿀 수 있다.
  - 잘못된 API로 쌓인 `source = 'musinsa'` 행은 마이그레이션 `018`에서 지운다. 선물하기 행은 건드리지 않는다.
  - 신청은 프리유저 가입 전까지 사람이 한다. 카드 링크를 PC에서 열어 직접 신청하고 `✅ 신청함`으로 기록한다(선물하기와 같다, 결정 10).
  - 자동 신청은 로그인이 필요하므로 프리유저 가입 뒤의 별도 단계로 나중에 Aside(내가 로그인한 브라우저)로 한다. 옵션을 고르는 Telegram 버튼을 만들고 신청한다. 리뷰 게시는 자동화하지 않는다(결정 10). 지운 Aside 코드는 git 기록에 남아 있다.
- **다시 검토할 때**
  - 스냅을 올리고 프리유저 가입을 마치면 상세·신청 API가 열리는지 실제로 확인하고, 그때 옵션 선택 버튼과 Aside 자동 신청을 설계한다. 잘못 신청하면 되돌리기 어려우니 신청 직전 확인 단계를 둔다.
  - 목록 API 형식이 바뀌면 `src/campaigns/musinsa.ts`의 스키마부터 고친다. 마감 시각은 날짜만 주므로 그날 끝으로 가정했다. 실제로 더 일찍 닫히면 마감 처리를 다시 본다.

## 14. 만료 초안은 버리지 않고 다시 쓴다

- **이유:** 검수를 못 해 만료된 초안이 1주에 3~4건씩 쌓였다(2026-10-18 기준 9건). 원문을 읽고 말투까지 맞춰 쓴 글이라 버리기 아깝다. 그중 절반쯤은 몇 주가 지나도 읽을 만한 글(사용법, 연구 결과, 설계 교훈)이고, 나머지는 시의성이 지난 소식이다.
- **결정**
  - 상록 초안은 LLM이 시점 표현만 고쳐서 다시 검수에 올린다(`/revive`). 사실과 말투는 바꾸지 않고, 고르는 것은 사람이 버튼으로 한다. 자동으로 다시 올리지 않는다.
  - 시의성이 지난 초안은 매주 일요일 "이번 주 놓친 소식" 연결 글 하나로 묶는다. 하나씩 내기엔 늦은 소식도 주간 정리 틀이면 읽힌다.
  - 묶음 글은 소식마다 출처 링크를 단다(`post_parts.link_url`, `016`). 링크를 마지막 답글 하나에만 다는 결정 8의 예외다. 출처가 세 개인데 링크를 하나만 달면 나머지 둘은 근거를 잃는다.
  - 재활용한 글은 `generation.text`도 새 글로 바꿔서, 문체 학습이 LLM의 수정을 주인의 수정으로 배우지 않게 한다.
- **다시 검토할 때:** 재활용 글과 묶음 글의 조회·답글이 일반 글보다 확연히 낮으면 묶음 주기를 늘리거나 그만둔다. 만료가 주 3건 이상 계속되면 하루 초안 수(`DAILY_POST_COUNT`)를 줄인다.
