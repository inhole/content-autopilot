# 체험단 자동화 계획과 현황 (카카오톡 선물하기, 무신사 프리유저)

카카오톡 선물하기 체험단의 공개 목록과 무신사 프리유저 체험단의 공개 목록을 모아 고르고, 신청·결과·리뷰 기한을 챙기고, 리뷰 초안을 쓰는 파이프라인이다. 동작은 [architecture.md](../architecture.md#체험단-파이프라인), 운영은 [operations.md](../operations.md#체험단), 결정과 이유는 [decisions.md](../decisions.md) 9~13을 본다. 구현하면서 바뀌는 결정은 이 문서와 `decisions.md`에 같이 적는다.

## 1. 방향이 바뀐 이유

처음 계획은 **레뷰(revu.net) 공고를 카카오톡 PC 단체방에서 읽고, Aside 브라우저로 신청하고, 네이버 블로그에 임시저장**하는 구조였다. 인터뷰 때 세운 가정이었는데 틀렸다.

- 실제로 하려는 체험단은 **카카오톡 선물하기 체험단**이다. 레뷰도 네이버 블로그도 쓰지 않는다.
- 선물하기 체험단 목록은 gift.kakao.com의 공개 JSON이다. 카톡을 읽을 필요가 없다.
- 신청과 리뷰 작성은 카카오톡 **모바일 앱 전용**이다. 데스크톱으로 열면 모바일 전용 안내 페이지로 간다. 신청 폼에는 옵션 선택과 배송지뿐이다.

그래서 카톡 읽기, 로컬 PC 워커, Aside, 레뷰 신청, 네이버 임시저장, `WORKER_ROLE`, dry-run을 모두 없앴다. 신청과 리뷰는 내가 폰에서 하고 Telegram 버튼으로 기록한다.

그 뒤 무신사 프리유저를 두 번째 출처로 붙였다. 처음에는 로그인이 필요한 다른 시스템(크리에이터 캠페인)을 체험단 목록으로 잘못 읽어서 Aside와 로컬 워커(`WORKER_ROLE=local`)를 도입했지만, 실제 체험단 목록은 로그인 없이 읽히는 공개 API였다. 그래서 둘 다 다시 지우고 선물하기처럼 클라우드 워커가 읽는다(섹션 7, 결정 13). Aside는 로그인이 필요한 자동 신청을 만들 때 다시 쓴다.

## 2. 구현한 것 (`feat/campaign-autopilot`)

마이그레이션 `014`(`campaigns`, `campaign_reminders`)와 `src/campaigns/`. 수집부터 카드, 리마인더, 리뷰 초안까지 클라우드 워커 하나가 두 출처를 함께 처리한다(섹션 7).

| 단계 | 내용 |
|---|---|
| 수집 | `gift-collect`가 하루 3번(09·15·21시, `GIFT_COLLECT_CRON`) 공개 목록 전체를 읽어 `campaigns`에 upsert한다. 상태와 내 기록은 건드리지 않는다. |
| 선별 | 규칙(제외 키워드·브랜드, `maxCompetition`, `minPriceWon`, 마감)으로 거르고, 남은 후보를 코드가 경쟁률·정가·관심 단어로 점수화해(`CAMPAIGN_RANK_MODE=rule`, 기본. `llm`이면 LLM이 60건씩) 출처마다 하루 `CAMPAIGN_DAILY_MAX`개를 뽑는다. |
| 카드 | 사진 카드에 경쟁률, `D-n (추정)`, 점수와 이유를 담고 `📱 선물하기에서 열기` / `✅ 신청함` / `🙅 패스`(사유 선택) 버튼을 붙인다. |
| 기록 | `✅` 뒤 `🎉 선정` / `😢 미선정`. `/due <번호> <날짜>`로 리뷰 기한. `/camps`로 진행 중 목록. |
| 유지보수 | `campaign-maintenance`가 매시 마감 지난 카드를 `EXPIRED`로 만들고, 09~21시에 리마인더(`result-check`, `due-missing`, `review-d3/d1/d0`)를 보낸다. |
| 리뷰 초안 | `📝 리뷰 초안 쓰기` → 안내 메시지에 메모 답장 → `review-draft` → 초안 메시지(복사용) + 조작 메시지(`🔁 다시 쓰기` / `✅ 리뷰 올림`). `수정:` 답장은 그대로 교체, 그 외 답장은 피드백. 광고 표기는 코드가 앞에 붙인다. |
| 대시보드 | 읽기 전용 웹 페이지([dashboard.md](../dashboard.md))와 `/status`에 체험단 단계별 개수. |
| CLI | `gift:list`, `musinsa:list`(둘 다 읽기 전용), `campaign:collect`, `musinsa:collect`, `campaign:rank`, `campaign:show`, `campaign:card`, `campaign:remind`, `review:draft` |

설정은 `GIFT_COLLECT_CRON`, `GIFT_TRIAL_PAGE_ID`(33325), `CAMPAIGN_DAILY_MAX`(5, 출처마다), `CAMPAIGN_RANK_MODE`(`rule`), `CAMPAIGN_PROFILE_PATH`(`config/campaign-profile.json`), `MUSINSA_COLLECT_CRON`(`0 10,16,22 * * *`)다.

## 3. 실제로 확인한 것 (2026-10-18)

- 공개 목록 API가 로그인 없이 응답한다. 첫 페이지 50건, 이후 24건씩 `collections?page=2…`로 이어지고, 마지막 페이지(19번째, 17건)에서 `paging.isLast = true`다. 합계 **475건**, 20페이지부터는 빈 `items`다.
- 페이지네이션이 끝까지 돈다. 같은 `campaignId`는 한 번만 담긴다.
- upsert가 멱등이다. 두 번 돌려도 새 행이 생기지 않고, 상태·점수·`updated_at`이 바뀌지 않는다.
- 형식 검증이 엄격하다. 필수 필드가 빠지거나 구조가 다르면 조용히 넘어가지 않고 실패한다.

### 무신사 (2026-10-19)

- 체험단 목록은 **공개 API**다: `GET https://www.musinsa.com/preuser/api/v1/event/events?page=N&size=100`(로그인 없음). 페이지는 1부터, `size`는 100까지(그 이상은 100으로 잘린다), 마지막 페이지는 `hasNext: false`이고 그 다음 페이지는 빈 `content`다. 352건이 4페이지였다. `/event/count`는 전체 개수, `/event/events/:id`는 상세(품목, 발표일, 배송일, 리뷰 기간, 옵션)다.
- 처음 읽었던 `influencer.musinsa.com/api2/mcmp/v2/recruitment-campaigns`는 로그인이 필요한 다른 시스템(크리에이터 캠페인, id 389xx, 55~83건)이라 카드 링크가 실제 체험단과 맞지 않았다. 그 행은 마이그레이션 `018`에서 지운다.
- 목록에 모집 인원(`recruitmentCount`)과 신청자 수(`applicantsCount`)가 있어서 선물하기처럼 경쟁률을 계산한다.
- 신청, 내 신청 내역은 로그인과 프리유저 가입이 필요하다. 가입하려면 스냅을 한 번 올려야 한다(`MCMP_001_006 작성한 스냅이 있는 회원만 신청할 수 있습니다`). 그래서 지금은 읽기만 되고 신청은 사람이 한다.

## 4. 아직 확인하지 못한 것

| 항목 | 왜 중요한가 | 확인 방법 |
|---|---|---|
| `remainingDays`의 의미 | 신청 마감 추정(오늘 + 남은 일수의 끝)과 `EXPIRED`, `result-check` 시점이 모두 여기에 달려 있다. 당일 마감이 0인지 1인지, 실제 마감 시각이 언제인지 모른다. | 마감일이 알려진 체험단을 며칠 추적해 `remaining_days` 변화와 카톡의 실제 마감을 비교한다 |
| 선별 품질 | 475건 중 하루 5개를 뽑는 것이 핵심이다. 규칙 점수(2026-10-24부터 기본)는 경쟁률이 낮은 것을 앞에 두지만, 제목만으로 취향을 읽지 못해 키즈 의류처럼 안 맞는 품목이 올라올 수 있다. | 첫 1~2주의 카드와 `🙅 패스` 사유를 모아 `excludeKeywords`·`preferKeywords`와 가중치를 조정한다. 안 맞으면 `CAMPAIGN_RANK_MODE=llm` |
| 실제 봇의 사진 카드 | 이미지 URL이 Telegram에서 받아지는지, 캡션이 1024자 안에서 보기 좋은지 확인하지 못했다. | `campaign:collect` 또는 `campaign:card <id>`로 실제 봇에 보낸다 |
| 폰에서 링크가 카톡으로 열리는지 | `gift.kakao.com/giftbox/trial-campaign/<id>`를 Telegram에서 폰으로 열었을 때 카카오톡 앱의 해당 체험단으로 가는지, 브라우저로 열리는지 모른다. 브라우저로 열리면 신청 동선이 늘어난다. | 폰 Telegram에서 카드 버튼을 눌러 본다 |
| 리뷰 초안 품질 | 메모만 근거로 한 100~500자 초안이 쓸 만한지, 글자 수 보정(줄이기·늘리기)이 자연스러운지 모른다. | 선정된 건으로 한 번 끝까지 돌려 본다 |
| 리마인더 시점 | `result-check`가 "신청 마감 하루 뒤"인 것이 실제 발표 시점과 맞는지 모른다. | 첫 신청 건의 실제 발표일과 비교한다 |
| 무신사 실제 봇 카드 | 경쟁률, 정가·할인가, 발표일·리뷰 기간이 카드에 보기 좋게 나오는지, `image.msscdn.net` 이미지를 Telegram이 받는지 확인하지 못했다. | `musinsa:collect`로 실제 봇에 보낸다 |
| 무신사 선별 품질 | 무신사 후보는 경쟁률(대부분 수십~수백 대 1), 품목, 정가로 판단한다. 점수가 취향과 맞는지 모른다. | 첫 1~2주 카드와 `🙅 패스` 사유를 모은다 |
| 무신사 마감 시각 | `endDate`는 날짜만 주므로 그날 끝으로 가정했다. 실제로 더 일찍 닫히는지 모른다. | 마감일에 신청 화면이 언제까지 열리는지 한 번 본다 |
| 무신사 상세 누락 | 새 공고의 상세 읽기가 실패하면 발표일·리뷰 기간이 비고, 선정 때 리뷰 기한이 자동으로 채워지지 않는다(`/due`로 직접 기록). | 로그의 `musinsa detail: … skipped` 빈도를 본다 |

## 5. 다음 단계

1. 위 미확인 항목을 첫 1~2주 운영하면서 확인한다. 가장 먼저 사진 카드와 폰에서 링크 열림을 본다.
2. `remainingDays` 실측 결과로 마감 추정을 고친다. 맞으면 `(추정)` 표시를 줄이는 것도 본다.
3. 선별 결과가 나오면 `config/campaign-profile.json`(`preferKeywords`, `interests`, `excludeKeywords`, `maxCompetition`)과 규칙 점수 가중치(`src/campaigns/rank.ts`)를 조정한다.
4. 무신사 카드를 1~2주 받아 보며 경쟁률과 카드 정보가 선별에 쓸 만한지, `🙅 패스` 사유를 본다.
5. **무신사 자동 신청**은 프리유저 가입 뒤의 다음 단계다. 스냅을 한 번 올려 가입하고, 신청 API가 열리는지 확인한다. 열리면 옵션을 고르는 Telegram 버튼을 만들고, 내가 로그인한 Aside 브라우저로 신청한다. 신청 직전 확인 단계를 두고, 리뷰 게시는 자동화하지 않는다(결정 10, 13).

## 6. 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 선물하기 목록 API 형식이 바뀌거나 막힌다 | 스키마를 엄격히 검사해 실패를 알린다(수집 job 최종 실패 시 Telegram ❌). 첫 페이지 실패는 에러, 이후 페이지 실패는 읽은 만큼 사용. 요청 간격 0.4초, 하루 3회. |
| 공개 API라도 약관·접근 제한이 있을 수 있다 | 읽기 전용, 낮은 빈도, 로그인·신청 자동화 없음. 문제가 보이면 `GIFT_COLLECT_CRON` 횟수를 줄이거나 끈다. |
| 마감 추정이 틀려 신청 가능한 카드가 일찍 만료된다 | 마감은 `(추정)`으로 표시하고, 실제 마감은 카톡에서 확인한다. 만료된 카드는 버튼이 지워지고 다시 살릴 수 없으므로(`campaign:card`로 다시 보내도 등록되지 않는다), 추정이 틀린 것으로 보이면 계산을 먼저 고친다. |
| 리뷰 초안이 써보지 않은 경험을 지어낸다 | 메모만 근거로 쓰게 하고, 사람이 읽고 직접 올린다. 코드는 게시하지 않는다. |
| 광고 표기가 빠진다 | 코드가 모든 초안 맨 앞에 붙인다(결정 12). |
| 기록 버튼을 빼먹어 리마인더가 어긋난다 | 결과 확인·기한 누락 리마인더가 되묻는다. `/camps`로 상태를 훑는다. |
| 무신사 공고의 상세 읽기가 실패한다 | 경고만 남기고 수집은 계속한다. 발표일·리뷰 기간이 비고 `/due`로 직접 기록하면 된다. 선물하기는 영향이 없다. |
| 무신사 목록 API 형식이 바뀌거나 막힌다 | 스키마를 엄격히 검사해 실패를 알린다(첫 페이지가 전부 형식 오류면 실패, 최종 실패 시 Telegram ❌). 읽기 전용, 페이지 간격 300ms, 하루 3회, 최대 20페이지. |
| 무신사 계정에 영향을 준다 | 로그인 없이 공개 목록만 읽는다. 신청, 글쓰기, 가입은 하지 않는다. 자동 신청을 붙일 때 다시 평가한다. |
