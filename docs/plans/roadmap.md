### 추천: A를 먼저 하고, B를 주간 작업으로 붙인다

> A(`/revive`)와 B(`weekly-digest`, `/digest`)는 구현했다(2026-10-19, `docs/architecture.md`의 「만료 초안 다시 쓰기」). 남은 것은 실제 LLM으로 판정·재작성 품질을 보고, 첫 일요일 묶음 글을 검수하는 일이다. C와 「만료 자체를 줄이기」는 아직이다.

**A. 상록 초안 재검수** (추천, 1일)
- `EXPIRED` 초안마다 LLM이 상록인지, 시의성이 지났는지 판정한다(`chatJson`, 한 번 호출로 여러 건).
- 상록이면 첫 줄과 "나왔다", "최근" 같은 시점 표현만 고친다. 사실 문장은 바꾸지 않고, 말투는 사용자 본인 음슴체를 유지한다.
- 고친 초안을 `PENDING_REVIEW`로 되돌려 기존 Telegram 검수로 다시 보낸다. 카드에는 `♻️ 재활용` 표시를 붙인다.
- 진입점은 Telegram `/revive`와 CLI `revive [postId]`다. 목록을 보여주고, 판정 결과와 함께 하나씩 고르게 한다. 시의성이 지난 글은 B로 넘긴다.
- 새 상태는 만들지 않는다. `EXPIRED → PENDING_REVIEW` 전이와 `revision` 증가로 처리하고, 원래 초안은 `generation`에 남겨 둔다.
- 9건 중 4건 정도가 바로 쓸 수 있다.

**B. 주간 "이번 주 놓친 소식" 연결 글** (2일)
- 매주 일요일 저녁 작업이 그 주에 만료된 초안과, 점수는 높았지만 하루 개수에 밀린 주제를 모은다.
- 그중 3개를 골라 연결 글 하나로 만든다. 본글은 묶음 소개와 1번, 답글 2개는 2·3번이고, 링크는 마지막 조각에 둔다(결정 8의 규칙).
- 하나씩 내기엔 늦은 소식도 "주간 정리"라는 틀이면 자연스럽다.
- 연결 글 발행 경로(`post_parts`, `publish-chain`)를 그대로 쓴다. 검수도 기존 Telegram 메시지(`수정2:` 등)로 한다.

**C. 숏츠/릴스 원고 재료** (4번 이후)
- 300자 안팎 초안은 40~60초 내레이션 분량이다. 4번 영상 파이프라인이 생기면 상록 초안을 첫 원고로 쓴다.

### 만료 자체를 줄이기

- 09시와 18시 리마인더에 더해, 만료까지 24시간 이하로 남은 초안에 "내일 만료" 예고를 한 번 보낸다(완료, `017`). 손대면 시계가 초기화되므로 그 뒤 다시 24시간 이하가 되면 또 보낸다.
- 하루 초안 수(`DAILY_POST_COUNT`, 기본 3)가 검수 여력보다 많으면 2로 줄인다. 만료가 주 3건 이상이면 줄이는 신호로 본다.

## 2. 체험단 남은 일

### 사용자가 먼저 할 일

- **무신사 프리유저 가입:** 무신사 스냅을 1개 이상 올린 뒤 프리유저에 가입한다. 그 전에는 상세, 신청, 내 신청 내역 API가 `MCMP_001_005` / `MCMP_001_006`으로 막힌다.
- **Aside 브라우저(자동 신청용):** 자동 신청을 만들 때 이 PC에서 Aside를 켜 두고 무신사에 로그인해 둔다. 목록 수집에는 필요 없다(공개 API, 클라우드 워커).

### 운영하면서 확인할 것

- 실제 Telegram 봇에서 사진 카드, 버튼, 오래된 버튼 거절이 동작하는지
- 실제 LLM의 선별 결과와 리뷰 초안 품질. 첫 1~2주 결과로 `config/campaign-profile.json`과 프롬프트를 조정한다.
- 선물하기 `remainingDays`의 의미(0이 오늘 마감인지)와 마감 추정이 맞는지
- 폰에서 Telegram 카드의 선물하기 링크를 열면 카톡으로 넘어가는지
- 첫 수집 때 475건이 한꺼번에 들어오면, 하루 5건만 카드가 되고 나머지는 `SKIPPED`가 된다. 의도한 동작인지 본다.

### 무신사 자동 신청 (가입 뒤, 2~3일)

1. 가입한 계정으로 신청 화면과 내 신청 내역 응답을 Aside로 받아 fixture로 저장한다. 추측으로 만들지 않는다.
2. 카드에 옵션 버튼(`🚀 L로 신청` 등)을 붙인다. 옵션이 하나면 `🚀 신청`만 둔다.
3. `campaign-apply` 큐를 만든다(Aside가 있는 이 PC에서만 처리하는 방법이 필요하다). Aside로 신청 화면(`/preuser/apply/<id>`)에서 옵션과 기본 배송지로 제출한다. 처음에 만들었다가 지운 claim 모델을 그대로 쓴다. 제출 전후로 내 신청 내역과 대조하고, `claim_seq`로 소유권을 확인하고, 3회 실패하면 `APPLY_FAILED`와 재시도 버튼을 띄운다.
4. 내 신청 내역으로 선정 여부를 자동 반영한다. 그 전까지는 지금처럼 버튼으로 기록한다.
5. 일주일은 dry-run(제출하지 않고 기록만)으로 운영한 뒤 켠다.

## 3. 대시보드 React + Vite + shadcn/ui 전환

> 1·2단계는 구현했다(2026-10-19). 같은 날 공식 shadcn 스킬(`.claude/skills/shadcn`)과 CLI로 UI를 다시 만들었다(PR #13: 사이드바, KPI 카드, 데이터 테이블, 시트 상세, 성과 차트, 테마 전환). `web/`의 React 앱이 현황, 체험단 목록·상세, Threads 글, 성과(7/30/90일 차트)를 보여주고, 같은 워커가 `/api/*`와 `web/dist`를 서빙한다(`docs/dashboard.md`). 로컬에서 실제 선물하기 데이터 415건으로 화면을 확인했다. Railway가 빌드 스크립트를 돌리는지는 배포 때 확인해야 한다. 서버 렌더링 페이지는 빌드가 없을 때의 대체 화면으로 남겨 두었다.

### 목표

지금 대시보드는 `node:http` 서버가 HTML 문자열을 그리는 읽기 전용 페이지다(`src/web/`). 이를 React 앱으로 바꿔 표, 필터, 차트를 쓸 수 있게 한다. 1단계에서는 지금 기능을 그대로 옮기고, 조작 기능은 2단계에서 따로 판단한다.

### 구조

- **프런트:** `web/` 폴더에 Vite + React + TypeScript + Tailwind CSS + shadcn/ui를 둔다. 의존성은 `web/package.json`에 분리해서 워커 의존성과 섞지 않는다.
- **API:** 지금 `src/web/data.ts`의 조회 함수를 그대로 쓰는 JSON API를 같은 워커에 붙인다(`/api/overview`, `/api/campaigns`, `/api/campaigns/:id`, `/api/posts`).
  - 인증은 지금의 Basic 인증과 GET 전용, 보안 헤더를 유지한다.
- **배포:** `web/dist` 정적 파일을 워커가 그대로 서빙한다. 서비스를 따로 늘리지 않는다.
  - 지금은 빌드 단계가 없다. 루트에 `build` 스크립트(`npm --prefix web ci && npm --prefix web run build`)를 추가하고 Railway(Railpack)가 이를 실행하는지 확인한다.

### 화면 (shadcn/ui 컴포넌트 기준)

| 체험단 상세 | 공고 정보, 선별 이유, 리마인더, 메모, 리뷰 초안 | Sheet, Separator |
| Threads 글 | 최근 50개, 상태와 성과 | Table |

### 관리자 콘솔 (후속 작업)

2026-10-19에 정했다. 대시보드를 "보는 곳"에서 "운영하는 곳"으로 바꾼다. Telegram에서 하던 조작을 웹에서도 할 수 있게 하고, Telegram 봇은 그대로 둔다(알림과 빠른 조작용).

**로그인: Telegram 1회용 코드만** (비밀번호 없음)

- 로그인 화면에서 `코드 받기`를 누르면 봇이 `TELEGRAM_CHAT_ID`로 6자리 코드를 보낸다. 웹에 그 코드를 넣으면 로그인된다. Telegram 계정을 가진 사람만 들어올 수 있으므로 계정 보안이 곧 콘솔 보안이다.
- 코드는 5분 동안 유효하고 한 번만 쓴다. 저장은 해시로만 한다(새 테이블 `admin_login_codes`: code_hash, expires_at, used_at, attempts).
- 틀린 입력은 코드당 5회까지만 받는다. 코드 요청은 1분에 1회, 시간당 5회로 제한한다. 제한에 걸리거나 로그인에 성공하면 Telegram으로 알린다(`🔐 관리자 콘솔 로그인`, 시각과 IP).
- 세션은 서명된 HttpOnly 쿠키다(`Secure`, `SameSite=Strict`, 30일, 서버 비밀값 `ADMIN_SESSION_SECRET`). 세션 목록을 DB(`admin_sessions`)에 둬서 `/logout`과 "모든 세션 끊기"가 즉시 먹게 한다.
- 지금의 Basic 인증(`DASHBOARD_PASSWORD`)은 콘솔이 배포되면 걷어낸다. `/healthz`와 `/go/gift/:id`는 계속 인증 없이 둔다.

**설계 원칙**

- 모든 쓰기는 Telegram 버튼이 부르는 것과 **같은 조건부 함수**를 부른다(`approvePost`, `applyReviewEdit`, `markApplied`, `markResult`, `setReviewDeadline` 등). 화면에 표시한 `revision`을 함께 보내서, 그 사이 Telegram에서 먼저 처리했거나 본문이 바뀌었으면 거절하고 화면을 새로 고친다. 경쟁 조건 처리는 지금처럼 DB 한 곳에 둔다.
- 웹에서 처리하면 Telegram의 해당 검수 메시지·카드 버튼을 지운다(`clearButtons`). 두 화면이 서로 다른 상태를 보이지 않게 한다.
- LLM을 부르는 일(재생성, 리뷰 초안, 판정)은 지금처럼 큐에 넣고, 화면은 진행 중 표시 뒤 결과가 오면 갱신한다. 웹 요청 안에서 LLM을 기다리지 않는다.
- API는 `POST /api/...`로 만들고, 쿠키 세션 + `Origin` 검사 + CSRF 토큰(세션별, 헤더로 전송)을 모두 확인한다. 응답 모양은 `src/web/api-types.ts`에 계약으로 먼저 정한다.
- 발행·폐기·즉시 발행처럼 되돌리기 어려운 조작은 확인 대화상자(shadcn `AlertDialog`)를 거친다.
- 모든 쓰기는 감사 기록을 남긴다(`admin_actions`: 시각, 세션, 조작, 대상, 결과).

**단계**

1. 로그인(Telegram 코드, 세션, CSRF, 감사 기록)과 Basic 인증 교체. 아직 쓰기 기능 없이 배포해 로그인만 검증한다.
2. 체험단 조작(위험이 낮음): 신청함·패스·선정·미선정·기한·리뷰 초안.
3. Threads 초안·예약 조작과 만료 초안·주간 묶음.
4. 운영 버튼(지금 수집 등)과 서버 렌더링 페이지 삭제.

**테스트:** 로그인 흐름(만료·재사용·시도 제한·요청 제한), CSRF·Origin 거부, revision 충돌 시 거절, Telegram 버튼 정리, 감사 기록을 통합 테스트로 확인한다. 화면은 Testing Library로 확인한다.

## 4. YouTube Shorts / Instagram Reels 확장

결정 1에서 미뤘던 영상 확장이다. 다시 볼 조건은 "Threads 발행이 안정적으로 돌고, 반응 좋은 주제 데이터가 쌓였을 때"였다. 발행 11건이 쌓였고 성과 수집도 돌기 시작했으므로 준비 단계부터 시작할 수 있다.

### 무엇을 영상으로 만드나

- **1순위:** 성과가 좋았던 Threads 글(`post_insights` 조회 상위)과 1번의 상록 초안. 30~45초 세로 영상으로 만든다. 구성은 제목 카드, 핵심 문장 3~4장면, 마지막 출처 장면이다.
- **2순위:** 체험단 리뷰 릴스. 선정된 체험단의 사진과 메모로 15~30초 리뷰 영상을 만든다. 사진·영상 소재는 사용자가 찍은 것만 쓴다.

### 파이프라인

```
원고(LLM, 장면 JSON) → TTS 내레이션 → 렌더(자막·장면·BGM) → 저장소 업로드 → Telegram 미리보기 검수 → 발행
```

| 단계 | 선택지 | 메모 |
|---|---|---|
| 원고 | `chatJson`으로 장면 배열 `{ 화면 문구, 내레이션, 길이 }` | 원글의 사실만 쓰고 말투 규칙을 지킨다 |
| TTS | OpenAI TTS, ElevenLabs, Google Cloud TTS | 한국어 품질과 단가를 샘플 3개로 비교해서 고른다 |
| 렌더 | Remotion(React) 또는 ffmpeg | 대시보드와 같은 React라 Remotion을 우선 검토한다. Railway Hobby는 CPU가 약하므로 렌더는 이 PC에서 따로 돌리는 워커에서 한다(필요해지면 워커 역할 구분을 다시 도입한다) |
| 저장소 | Supabase Storage(공개 URL) | Instagram 컨테이너가 `video_url`을 요구한다 |
| 검수 | Telegram `sendVideo` + 승인·재생성 버튼 | Threads 검수와 같은 revision 규칙을 쓴다 |

### 플랫폼별 발행

- **Instagram Reels**
  - Instagram 프로페셔널 계정(크리에이터 또는 비즈니스)과 `instagram_content_publish` 권한이 필요하다.
  - Threads용 Meta 앱에 Instagram 제품을 추가할 수 있는지부터 확인한다. 개발 모드에서 본인을 테스터로 쓰는 방식이 될 가능성이 있다.
  - 발행은 `media_type=REELS` 컨테이너를 만들고 `FINISHED`를 기다린 뒤 `media_publish`하는 흐름이라 Threads와 같다. 지금의 claim 모델과 `driveContainer` 패턴을 그대로 쓴다. 저장은 `posts.platform`으로 구분한다.
- **YouTube Shorts**
  - YouTube Data API v3 `videos.insert`(resumable upload)를 쓴다.
  - 검증되지 않은 API 프로젝트로 올린 영상은 비공개로 고정되므로 감사(audit) 신청을 제일 먼저 한다.
  - OAuth 동의 화면이 Testing이면 refresh token이 7일 만에 만료되고, `youtube.upload`는 민감 범위라 앱 검증이 필요하다.
  - 감사를 통과하기 전에는 Telegram으로 받은 영상 파일을 사람이 직접 올린다.

### 단계

| 단계 | 내용 | 끝났다고 보는 기준 |
|---|---|---|
| V0 | 계정·API 확인: Instagram 프로페셔널 계정 전환, Meta 앱 권한, Google Cloud 프로젝트와 YouTube 감사 신청, TTS 샘플 비교 | 각 API로 테스트 업로드 1건 |
| V1 | 원고 + TTS + 렌더를 로컬 PC에서 돌리고, Telegram으로 미리보기를 받아 직접 올린다 | 주 3편을 손으로 올릴 수 있음 |
| V2 | Reels 자동 발행 (컨테이너 claim 모델) | 승인한 영상이 정해진 시간에 올라감 |
| V3 | Shorts 자동 발행 (감사 통과 뒤) | 공개 업로드 성공 |
| V4 | 영상 성과 수집과 주간 리포트 통합 | `/report`에 영상 줄 추가 |

### 리스크

- 남의 글을 재가공한 영상은 노출이 줄 수 있다. YouTube는 대량 생산한 콘텐츠의 수익화를 제한한다(결정 3). 원고에 개발자 관점 해석 한 줄을 반드시 넣고, 같은 틀의 영상을 하루 1편 이상 올리지 않는다.
- 렌더와 TTS 비용, 로컬 PC가 꺼져 있을 때의 지연이 생긴다. 렌더 대기열은 PC가 켜지면 처리한다.
- 영상 검수는 글보다 오래 걸린다. 미리보기는 짧은 저해상도 버전으로 먼저 보낸다.
